# 0.13 — Stable editor embedding and project playgrounds

Status: pending. Depends on 0.12 for the complete product baseline; editor-only
contract work may be prepared earlier after 0.3. Contracts: C1/C9/C11.

**User outcome:** embed code display/editing without loading an IDE, or embed a
project playground explicitly when execution is required.

## Ordered tasks

### V13-01 — Freeze the full/lite public contract

- Paths: `packages/frontend/web-editor/src/index.d.ts`, full/native-lite implementations,
  public API docs, examples, and build type-copy script.
- Inventory attributes, properties, methods, events, defaults, boolean coercion,
  value-before-upgrade behavior, theme tokens, sizing, readonly, and error semantics.
- Keep full/lite capability differences explicit. Align runtime behavior, declarations,
  and documentation; add new API only when needed for an actual consumer scenario.
- **Acceptance:** contract tests cover programmatic/user updates without event loops,
  late registration, empty value, property-versus-attribute precedence, and ready lifecycle.

### V13-02 — Consumer integrations and lifecycle

- Paths: editor demo and browser integration fixtures for plain HTML, Angular, React,
  and Vue. These are embedding hosts, not a new project-language support commitment.
- Verify mount/unmount/remount, multiple instances, lazy language races, form/page
  layout changes, keyboard, touch, and accessible labeling.
- Release CodeMirror views, observers, subscriptions, and workers when appropriate.
  Read-only lite must not summon an unwanted editing keyboard on iPad.
- **Acceptance:** A13 editor cases, no cross-instance state, no accumulating resources,
  and documented integration examples that execute in actual browsers.

### V13-03 — Distribution, types, and bundle isolation

- Paths: web-editor build/scripts/package metadata, install CLI, release workflow.
- Produce immutable versioned full/lite artifacts and type declarations; keep a rolling
  alias as convenience. Verify the installer can select a version and reports failures.
- Enforce current size budgets and absence of runtime/workbench imports. Remove legacy
  duplicate entries only after identifying consumers and providing migration notes.
- **Acceptance:** an empty consumer project installs a pinned version using documented
  commands and typechecks; no unexpected runtime network boot or preview dependencies.

### V13-04 — Embedded workbench route and host protocol

- Paths: proposed `apps/web/src/app/routes/embed.page.ts`, shared workbench composition,
  protocol types, and minimal host helper/demo.
- Compose the existing workbench with selected panels, never copy its state logic.
  Define versioned ready/load-project/change/error/run/dispose messages, limits, and
  acknowledgement behavior. Validate origin, source, schema, and project paths.
- Load a bounded snapshot; choose persistence explicitly and isolate projects between
  embeds. Receiving source does not authorize execution or grant host credentials.
- **Acceptance:** a host page loads a TS demo, receives changes, runs it through an
  allowed user action, and disposes it. Forged messages cannot replace another session.

### V13-05 — Embed capability fallback and documentation

- Paths: embedded route, capability service, preview providers, docs/demo.
- Test host iframe/security policies and isolation prerequisites against real deployment
  headers. Support certified static playground where possible and offer “open in Vertex”
  when the host context cannot execute; retain editing inside the embed.
- Document separate costs, supported features, origin requirements, and integration
  examples for editor versus playground. The host is not forced to configure runtime
  headers merely to display an editor.
- **Acceptance:** plain HTML editor works without a WebContainer boot; a certified
  embedded project executes under its documented policy, including iPad where advertised.
  Unsupported embedding clearly identifies the limitation rather than hanging.

## Exit demonstration

Show three examples: read-only snippet, editable code input, and a project playground.
Inspect each network/bundle profile and prove only the third starts an execution runtime.
