# 1.0 — Stable release acceptance

Status: pending. Depends on 0.16 and all required gates. Version 1.0 is a certification
of defined workflows, not a final feature sprint or a promise of VS Code parity.

## Mandatory acceptance checklist

- [ ] Shared CodeMirror editing behavior across workbench surfaces; independent full/lite API.
- [ ] Persistent workspace identity, byte-safe file operations, revision-aware saves,
      recovery, migration, and concurrent-writer protection verified.
- [ ] Create/open/import/export, explorer, quick open, search/replace, preferences,
      per-document undo, and two-group editing meet their contracts.
- [ ] Project-aware JS/TS assistance, navigation, rename, diagnostics, formatting,
      and documented lint support work on certified fixtures.
- [ ] Native terminal/process lifecycle and supported browser runtime share current
      source with the editor; both synchronization directions are verified.
- [ ] Certified TS/frontend projects install/run/preview/test/build as advertised;
      unsupported toolchains produce clear capability limitations.
- [ ] Git status/diff/stage/commit/branches and authenticated remote workflows work,
      including safe conflict resolution and abort/recovery.
- [ ] iPad M1 physical keyboard/touch/suspension workflow is verified, including a
      useful TS execution path accepted by the owner.
- [ ] Phone basic editing and accessible keyboard/VoiceOver journeys are verified.
- [ ] Standalone editor consumers and project embedding have versioned, tested contracts.
- [ ] Static artifact export and integrated Cloudflare Pages publishing are verified
      against an owned test destination with credentials isolated from project code.
- [ ] Performance budgets and lifecycle resource checks pass on recorded environments.
- [ ] Signed/notarized macOS artifact, immutable editor bundles/types, hosted web app,
      and documentation are tied to tested commits and artifact manifests.
- [ ] Setup, support matrix, limitations, recovery, update, and credential instructions
      match actual behavior; no pending mandatory physical/external checks remain.
- [ ] No unresolved silent data loss, secret exposure, privilege escalation, or blocker
      to a certified primary workflow.

## Final tasks

### V100-01 — Review evidence and product claims

- Paths: milestone evidence, public support matrix, and this acceptance checklist.

Compare the checklist with milestone evidence and real-project outcomes. Verify
that every “supported” statement names a tested platform/template/version. Unchecked
mandatory entries block the release; the owner explicitly decides any scope change.

- **Acceptance:** every mandatory item has reviewed evidence for the candidate;
  no unresolved release blocker is hidden in a general limitation list.

### V100-02 — Prepare release artifacts and release notes

- Paths: package/Tauri version metadata, release CI, artifact manifest, changelog,
  and upgrade documentation.

Apply the agreed package/product version policy, produce release notes and checksums,
and identify exact tested artifacts. Include compatibility/migration guidance and
known non-blocking limitations. Publishing requires the owner's existing release
authorization; preparing reviewable artifacts does not itself publish them.

- **Acceptance:** versions, checksums, commit, and validation match the prepared
  artifacts; authorization or missing external prerequisites are recorded accurately.

### V100-03 — Publish and verify the release

- Paths: established release/deployment workflows and the release evidence manifest.

Using the established authorization and pipeline, publish the web/docs artifacts,
macOS package, and versioned editor bundles. Smoke-test the delivered URLs/installers
and recovery instructions. Record deployment/release IDs and an incident rollback path.
Do not claim publication if credentials or an external approval are still unavailable.

- **Acceptance:** actual delivered artifacts pass their smoke checks and match the
  manifest; release IDs and rollback instructions are available to the operator.

### V100-04 — Establish maintenance and the next roadmap

- Paths: support/security/contributing documentation, issue templates, and post-1.0 plan.

Document bug-report requirements, severity handling, supported-version policy, and
how data-safety/security patches reach users. Route discovered defects to 1.0.x.
Prepare 1.x improvements from actual use and a separate 2.0 extension-compatibility
study; Windows/Linux and broader languages remain explicit expansions.

- **Acceptance:** users can identify supported versions and report reproducible
  failures; maintenance work and expansion research have separate owners/queues.

## Version 2 handoff

Carry forward the extension-compatibility ambition without retroactively making it
a 1.0 dependency. Establish a fixed extension corpus, per-platform execution model,
API coverage, licensing/distribution constraints, and behavioral tests before claiming
“50% compatible.” The internal command/provider seams delivered here are useful
foundations, not an implementation of the VS Code extension host.
